# Design Doc: Multi-Channel Order Reconciliation

Short architecture overview. Every design choice below maps to a constraint in the project brief.

## Constraint → Choice map

| Brief constraint | Design choice |
| --- | --- |
| Four channels report financials differently; gross alone will not balance | Canonical order model storing decomposed financials (gross / discounts / commission / paid) |
| Genuine repeat order indistinguishable from feed duplicate; neither may be silently merged | Deterministic matching policy with a confidence threshold + explicit **ambiguous** bucket |
| Cancelled order may already be cooked | Cancellations kept in history; `cancelled ∧ cooked` recorded as a first-class exception |
| Closed day must never mutate | Close-then-adjust: closes are immutable snapshots; late settlements append adjustments linked to the original close |
| Contradicting T+2 settlement must be traceable | Adjustments carry FK links: adjustment → settlement → order → original close |
| Feeds/settlements generated by the system with injected disagreements | Synthetic generator writes feeds **and** ground truth in the same pass |
| Output must be checkable | Validation runner diffs reconciliation output against generated ground truth |

## Architecture

```
                    ┌─────────────────────────────┐
                    │  Synthetic Data Generator   │  feeds + ground truth
                    └──────┬──────────┬───────────┘
          POS/app/agg feeds│          │kitchen confs + T+2 settlements
                           ▼          ▼
              ┌──────────────────────────────────┐
              │  Ingestion Adapters (per source) │  normalize → canonical order
              └──────────────┬───────────────────┘
                             ▼
                    ┌──────────────────┐
                    │  Matching Engine │  strong IDs / fuzzy / ambiguous
                    └────────┬─────────┘
                             ▼
                    ┌─────────────────────────┐
                    │  Reconciliation Engine  │  unpaid / uncooked / financial variance
                    └────────────┬────────────┘
                                 ▼
                    ┌─────────────────────────┐    ┌──────────────────┐
                    │  Daily Close (immutable)│───▶│  Exception Queue │
                    └────────────┬────────────┘    └──────────────────┘
                                 ▼
                    ┌─────────────────────────┐
                    │  Settlement Processor   │  adjustments, never rewrites
                    └─────────────────────────┘
                                 ▼
                    ┌─────────────────────────┐
                    │  Validation Runner      │  output vs ground truth
                    └─────────────────────────┘
```

Components: Node.js (TypeScript) services exposed over a small REST API; React UI reads closes, exceptions, and adjustments. All writes are append-only; nothing is mutated after the fact.

## Key decisions and trade-offs

### 1. Canonical model with decomposed financials
Each channel normalizes to one schema that keeps gross, discounts, commission, and paid amounts as separate fields, plus a source map retaining original IDs.

**Trade-off:** more schema surface than a single "amount" column, but required — comparing gross alone cannot detect commission/discount mismatches that the aggregators report differently.

### 2. Deterministic matching over ML
Matching uses explicit rules: strong order IDs → confident match; attribute similarity above a threshold → ambiguous; below → no match. Ambiguous and no-match records go to the exception queue.

**Trade-off:** deterministic matching under-detects some edge cases an ML model might catch, but it is auditable, explainable, and reproducible against ground truth. Because the brief forbids silently merging genuine repeats with feed artefacts, a rule engine with an explicit "cannot decide" state is the honest design; ML would add non-determinism that breaks validation.

### 3. Close-then-adjust (append-only)
A close is a versioned, immutable record of the day as known at close time. A late settlement never edits it; the settlement processor creates an adjustment record with a traceable chain.

**Trade-off:** figures can transiently disagree with the "true" settlement until the adjustment is reviewed. This is deliberate — it preserves auditability and prevents silent retroactive edits, which the brief explicitly requires. Downstream consumers must sum closes + adjustments, never read a close alone.

### 4. Reconciliation on decomposed variance classes
Variances are classified: unpaid, uncooked, commission mismatch, discount mismatch, timing. Each class maps to a reason code used both in reports and in ground-truth validation.

**Trade-off:** classification logic must be maintained per class, but it makes exceptions actionable and lets validation assert on reason codes, not just totals.

### 5. Cancellations are history, not deletions
Cancelled orders remain; if the kitchen already confirmed cooking, a `CANCELLED_AFTER_COOKING` exception is raised.

**Trade-off:** cancelled-but-cooked records stay in the financial picture (and cost the restaurant), which is the point — deleting them would hide the loss.

### 6. Generated data = feeds + ground truth in one pass
The generator writes the four channel feeds, kitchen confirmations, and settlement files while recording the intended truth for every injected disagreement.

**Trade-off:** generator and reconciler share shape definitions, so a generator bug can mask a reconciler bug. Mitigated by keeping the generator deliberately simple and independently reviewed, since the brief mandates self-generated feeds.

### 7. Local JSON store
Single-process JSON-file store; no external database service.

**Trade-off:** fine for the exercise's local batch workloads and predictable volumes; would be swapped for Postgres behind a thin repository interface if concurrency, server multi-tenancy, or WAL durability is needed.

### 8. Batch pipeline, not streaming
Reconciliation runs as ordered CLI/API steps (generate → ingest → match → reconcile → close → settle → validate).

**Trade-off:** no real-time guarantees; fine because the brief centers on end-of-day reconciliation and T+2 settlements, not live event processing.

## Failure/semantics guarantees

- **Idempotent ingestion:** re-ingesting a feed with the same (source, external_id) is a no-op, preventing double-counting when the same order appears in two feeds.
- **No silent merges:** any record lacking a confident match is surfaced, never silently absorbed.
- **Immutable closes:** enforced at the repository layer (no update path exists for a close row, only inserts).
- **Traceable adjustments:** every adjustment carries links to settlement, order, and original close; chain integrity is part of validation.

## Open questions
- Manual-review workflow for the exception queue (UI only vs. approve/reject mutations to an adjustment status).
- Currency/timezone handling beyond a single configured restaurant timezone.
